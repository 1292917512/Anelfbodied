# 在 Anelf 频道回复中控制桌宠

当当前用户消息包含“桌宠客户端接入”上下文时，AnelfBodied 会解析这一轮 Agent 的回复。此模式不要求 Agent 再连接用户电脑的 MCP，也不需要获得本机控制 Token。

普通文字回复会显示为桌宠气泡。需要执行动作时，整个回复必须是一个合法的 `desktop-pet/1` JSON 对象；不要添加前后说明、代码围栏或多个 JSON 对象。

## 会话与有效期

- 从本轮客户端接入上下文取 `session`，逐字使用，不随机生成，也不使用 Anelf 的频道 `sessionId` 替代。客户端会忽略旧轮次的动作。
- 为每个新批次生成唯一 ID，并计算当前 Unix 毫秒有效期，最多五分钟。上下文中的示例 ID 不是可反复使用的任务 ID。
- `commands` 的结构见[表达](../control/expression.md)、[移动](../control/movement.md)和[交互](../control/interaction.md)；批次规则见[执行与恢复](../control/execution.md)。
- 必须先得到具体数值再输出 JSON，不能把 `Date.now()`、注释或占位符直接写进回复。没有可靠时间来源时使用本轮接入上下文中仍有效的期限，不臆造未来日期。

## 回执事件

含 `ask` 的批次会自动回传回执；其他动作需要结果时设置批次级 `returnReceipt:true`。不需要后续处理的展示可省略该字段，避免无意义的对话往返。

回传消息的结构为 `{"type":"desktop-pet.receipt","receipt":...}`，其中 `receipt` 是实际批次回执。只有其中的真实 `answer` 才是用户回答。用回执中的 `id` 关联原批次，以 `status` 和逐步 `results` 判断可继续的步骤。

收到事件不代表必须再执行动作。仅在用户任务确实需要下一步时提交新批次；不要为每份回执发送“收到”并再次要求回执，形成循环。需要显示结束语时，可回复简短普通文字或不要求回执的 `say`。

Anelf 频道的命令按频道地址、用户和会话隔离。本机 MCP/HTTP 的 `pet_state` 不会查询到这些频道命令，不能因为查询为空就重新执行。使用频道回传事件或桌宠回执面板核对结果。

## 中断与恢复

客户端会重连 SSE、补充历史显示，但不会执行历史中的旧指令。没有收到回执时不盲目发送相同动作的新 ID。若本轮已停止或更换了客户端 `session`，等待新的用户任务和有效上下文。

频道模式的纯回复 JSON 没有取消或配置动作，不能在 `commands` 中伪造 `cancel`、`configure`。需要管理连接或停止远端会话时，使用已有且获授权的 MCP [频道管理](../control/connection.md)工具，或让用户使用桌宠的停止入口。
